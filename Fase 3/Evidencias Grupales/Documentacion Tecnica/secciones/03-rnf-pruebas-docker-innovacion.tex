\section{Requisitos no funcionales}
\label{sec:rnf}
Se mantienen RNF-01 a RNF-12 y sus enunciados/criterios de la matriz MoSCoW de Fase 3.
Los criterios siguientes son \textbf{transcritos de esa matriz}, no umbrales nuevos ni
resultados medidos. Su ratificación por el equipo/docente no consta en esta revisión.
Las brechas de definición se señalan explícitamente; no se agregan propuestas de umbral.

\subsection{RNF-01 — Interfaz clara e intuitiva}
\textbf{Categoría / prioridad:} Usabilidad / Must have.\par
\textbf{Enunciado:} La plataforma debe tener una interfaz simple y comprensible tanto para ciudadanos como para organizadores sin conocimientos técnicos.\par
\textbf{Criterio de aceptación existente:} Se ejecuta una prueba de usabilidad con usuarios representativos y se registran hallazgos, severidad y acciones de mejora. La muestra y umbral de aprobación deben acordarse con el equipo.\par
\textbf{Método y límite:} Prueba con usuarios representativos y registro de tareas/hallazgos. Muestra y umbral pendientes de definición.\par
\textbf{Evidencia local / estado registrado:} Pendiente de validación. Acordar muestra/umbral y registrar prueba de usabilidad con usuarios representativos.\par
\textbf{Referencia de implementación:} Documentacion Metodologica/\par

\subsection{RNF-02 — Diseño responsive / multiplataforma}
\textbf{Categoría / prioridad:} Compatibilidad / Must have.\par
\textbf{Enunciado:} La interfaz web debe adaptarse correctamente a distintos tamaños de pantalla y funcionar de forma consistente entre la versión web y la móvil.\par
\textbf{Criterio de aceptación existente:} Las vistas principales se renderizan correctamente de 320 px a escritorio; navegación de tab bar en móvil y barra superior en escritorio.\par
\textbf{Método y límite:} Recorrido responsive de vistas principales a 320 px y escritorio, más matriz de navegadores y dispositivos. No ejecutado en esta revisión.\par
\textbf{Evidencia local / estado registrado:} Parcial. Diseño responsive y navegación dual implementados. Falta matriz de navegadores/dispositivos y prueba de 320 px a escritorio.\par
\textbf{Referencia de implementación:} src/app/layout/main-layout/; android/\par

\subsection{RNF-03 — Tiempos de carga aceptables}
\textbf{Categoría / prioridad:} Rendimiento / Should have.\par
\textbf{Enunciado:} Las búsquedas y listados de eventos deben responder en tiempos razonables aun cuando la base de datos crezca.\par
\textbf{Criterio de aceptación existente:} Con un catálogo de referencia de 1.000 eventos publicados, las consultas paginadas de listado y filtros deben medir p95 menor o igual a 2 segundos. La metodología y el entorno de prueba deben quedar registrados.\par
\textbf{Método y límite:} Medición de consultas paginadas y filtros sobre catálogo de referencia; registrar entorno, volumen y distribución p95. No hay medición de aceptación actual.\par
\textbf{Evidencia local / estado registrado:} Pendiente de medición. Paginación visual no equivale a paginación de consultas. Medir p95 $\leq$2 s con 1.000 eventos, entorno y metodología; no afirmar mejora sin medición.\par
\textbf{Referencia de implementación:} src/app/core/services/eventos.service.ts; src/app/pages/calendario/calendario.page.ts\par

\subsection{RNF-04 — Protección de datos de usuarios y organizadores}
\textbf{Categoría / prioridad:} Seguridad / Must have.\par
\textbf{Enunciado:} Las credenciales y datos personales de los usuarios deben almacenarse y transmitirse de forma segura.\par
\textbf{Criterio de aceptación existente:} Las credenciales no se almacenan en el código; el transporte usa HTTPS y el acceso a datos respeta las políticas de fila.\par
\textbf{Método y límite:} Inspección de cliente/build y HTTPS; pruebas de aislamiento RLS/Storage, registro y recuperación con cuentas distintas. Configuración remota no inspeccionada.\par
\textbf{Evidencia local / estado registrado:} Parcial. Auth y funciones Edge presentes; panel sin credenciales demo. Verificar HTTPS, secretos fuera del cliente, aislamiento RLS/Storage y abuso del registro/reset. Registro sin verificación no acredita propiedad del buzón.\par
\textbf{Referencia de implementación:} src/app/core/services/supabase.service.ts; supabase/functions/; supabase/migrations/20261024000100\_password\_reset\_tokens.sql\par

\subsection{RNF-05 — Control de acceso por rol}
\textbf{Categoría / prioridad:} Seguridad / Must have.\par
\textbf{Enunciado:} El sistema debe distinguir permisos entre visitante, usuario registrado y administrador. El rol de organizador requiere un modelo de propiedad explícito antes de habilitar publicación o edición propia.\par
\textbf{Criterio de aceptación existente:} Las acciones protegidas se validan por rol y por propiedad. No se declara control por organizador hasta implementar la relación entre cuentas y organizadores.\par
\textbf{Método y límite:} Pruebas negativas sin sesión, visitor/editor/OAuth, cambio de rol y acceso directo a funciones; verificar propiedad. Pendiente ejecución registrada.\par
\textbf{Evidencia local / estado registrado:} Parcial. El guard exige profiles.role=admin y proveedor email; rechaza visitor, editor y Google. En servidor, admin-eventos valida getUser y profiles.role, y rechaza app\_metadata.provider cuando existe como cadena y difiere de email; no hay prueba ejecutada para identidades sin ese campo. Publicación aún usa user\_metadata.rol de autoservicio: definir alcance de organizador y propiedad estable. Faltan pruebas negativas y aislamiento.\par
\textbf{Referencia de implementación:} src/app/core/services/admin-auth.service.ts; src/app/pages/admin/admin.guard.ts; supabase/functions/admin-eventos/index.ts; supabase/functions/publicar-evento/index.ts\par

\subsection{RNF-06 — Disponibilidad del servicio}
\textbf{Categoría / prioridad:} Disponibilidad / Should have.\par
\textbf{Enunciado:} El servicio debe mantenerse disponible de forma estable con la infraestructura definida: base de datos administrada en Supabase, web desplegada en Vercel y ejecuciones automatizadas en GitHub Actions.\par
\textbf{Criterio de aceptación existente:} La web responde en el hosting definido y las ejecuciones automáticas se registran en scrape\_runs con su estado.\par
\textbf{Método y límite:} Sondeos fechados de web y registros scrape\_runs/CI; ventana y umbral de disponibilidad no definidos. CI histórico no constituye SLA.\par
\textbf{Evidencia local / estado registrado:} Parcial. Documentación registra runs \#18–\#25 en verde y DEF-CI-001 por horario fuera de ventana esperada. Verificar hosting vigente y monitoreo. Sin comprobación remota en esta revisión.\par
\textbf{Referencia de implementación:} Documentacion Tecnica/secciones/03-rnf-pruebas-docker-innovacion.tex\par

\subsection{RNF-07 — Soporte de crecimiento de datos}
\textbf{Categoría / prioridad:} Escalabilidad / Should have.\par
\textbf{Enunciado:} El modelo de datos y la arquitectura deben poder soportar un crecimiento sostenido en el número de eventos y organizadores sin degradar el servicio.\par
\textbf{Criterio de aceptación existente:} Al crecer el catálogo, el pipeline pagina y sincroniza por lotes sin cargar respuestas completas en memoria; re-ejecutar no duplica registros.\par
\textbf{Método y límite:} Carga incremental con medición de memoria y reejecución idempotente. Volumen, tolerancia y degradación admisible pendientes de definición.\par
\textbf{Evidencia local / estado registrado:} Parcial. Diseño por lotes/upserts documentado; falta prueba de crecimiento, memoria y reejecución sin duplicados. Diseño no equivale a prueba de carga.\par
\textbf{Referencia de implementación:} \nolinkurl{tmp_scraper_repo/}; \nolinkurl{src/app/core/services/eventos.service.ts}\par

\subsection{RNF-08 — Consistencia y normalización de la información}
\textbf{Categoría / prioridad:} Calidad de datos / Must have.\par
\textbf{Enunciado:} La información proveniente de distintas fuentes públicas debe normalizarse en fechas, ubicaciones y categorías para evitar inconsistencias o duplicados.\par
\textbf{Criterio de aceptación existente:} Eventos de distintas fuentes comparten fechas normalizadas, ubicación canónica y categorías; no se publican duplicados por URL original o clave compuesta.\par
\textbf{Método y límite:} Muestras de distintas fuentes y comparación por URL/clave, fechas y ubicación. Muestra y tolerancia de defectos pendientes de definición.\par
\textbf{Evidencia local / estado registrado:} Completado (implementación). Normalización/deduplicación implementadas; validar muestras actuales de fuentes y publicaciones de organizadores.\par
\textbf{Referencia de implementación:} tmp\_scraper\_repo/; Documentacion Tecnica/secciones/02-datos-uml.tex\par

\subsection{RNF-09 — Código mantenible y documentado}
\textbf{Categoría / prioridad:} Mantenibilidad / Should have.\par
\textbf{Enunciado:} El proyecto debe seguir buenas prácticas de desarrollo y mantener documentación mínima que permita a los tres integrantes del equipo dar mantención al sistema.\par
\textbf{Criterio de aceptación existente:} El repositorio mantiene documentación actualizada y las pruebas se ejecutan con un comando estándar.\par
\textbf{Método y límite:} Reproducción documental y comandos estándar en entorno identificado. Logs históricos disponibles; no prueban aptitud de mantenimiento por los tres integrantes.\par
\textbf{Evidencia local / estado registrado:} Parcial. Documentación Fase 3 revisada al 31-10 y PDF regenerados. Antecedente 23/23 del 27-10 no reejecutado; ejecutar controles afectados y registrar commit de entrega autorizado.\par
\textbf{Referencia de implementación:} package.json; Documentacion Tecnica/Documento\_Tecnico\_Capstone.pdf; Documentacion Metodologica/; Respuesta a la evaluación.docx\par

\subsection{RNF-11 — Despliegue reproducible}
\textbf{Categoría / prioridad:} Portabilidad / Must have.\par
\textbf{Enunciado:} El proyecto debe poder desplegarse de forma reproducible usando el stack definido (GitHub, GitHub Actions, Vercel, Capacitor/Android Studio), facilitando la integración continua entre los integrantes.\par
\textbf{Criterio de aceptación existente:} El repositorio debe incluir Dockerfile(s), docker-compose, variables de entorno documentadas e instrucciones reproducibles de levantamiento para los componentes aplicables.\par

\textbf{Evidencia local / estado registrado:} Parcial (decisión docente pendiente). Criterio original exige Dockerfile y compose, ausentes por decisión del equipo. No se elimina para simular cumplimiento: acordar excepción docente o implementar artefactos; comprobar despliegue reproducible.\par

\subsection{RNF-12 — Buenas prácticas de accesibilidad web}
\textbf{Categoría / prioridad:} Accesibilidad / Could have.\par
\textbf{Enunciado:} La interfaz debería seguir criterios básicos de accesibilidad (contraste, tamaños de fuente, navegación por teclado) para ampliar su alcance a más usuarios.\par

\textbf{Método y límite:} Auditoría automática y revisión manual de teclado, foco, contraste y lector. axe histórico contiene hallazgos; no se declara WCAG AA aprobada.\par
\textbf{Evidencia local / estado registrado:} Parcial. Avisos con alert/status, fondo sólido, iconos y cierre accesible. Falta auditoría WCAG 2.2 AA, teclado y lector con contraste medido. Publicar redirige a los 1,8 s: no afirmar persistencia universal de avisos.\par
\textbf{Referencia de implementación:} src/app/pages/login/login.page.html; src/app/pages/publicar-evento/publicar-evento.page.ts; src/app/pages/restablecer-contrasena/restablecer-contrasena.page.ts\par

\section{Despliegue sin Docker y brecha de aceptación}
\label{sec:docker}
La estrategia documentada usa GitHub Actions para scraper, Vercel para SPA,
Supabase administrado y Capacitor para Android. RNF-11 conserva un criterio que exige
Dockerfile(s) y docker-compose para componentes aplicables. No se encontraron esos
artefactos en las fuentes revisadas: hay una \textbf{brecha documental de aceptación},
no una excepción docente demostrada. No se añade Docker ni se cambia código funcional.
Despliegue efectivo, configuración de correo, RLS/Storage y funcionamiento nativo
requieren evidencias independientes del build.

\section{Innovación y límites del MVP}
\label{sec:innovacion}
La aportación es reunir fuentes heterogéneas en un catálogo con procedencia, normalización,
deduplicación y vigencia; el scraper reutiliza checkpoints y enriquecimiento selectivo.
Las recomendaciones del frontend se calculan por afinidad, no se describen como un LLM.
No se cuantifican ahorro, latencia, usuarios o eventos vigentes sin medición fechada.
El mapa puede usar ubicaciones aproximadas; no son coordenadas exactas certificadas.
El MVP no acredita pagos ni monetización; propuestas comerciales quedan fuera de alcance.
